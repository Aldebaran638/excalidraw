# Excalidraw 分支与发布

本规范取代此前将 `master` 用作产品主分支、将 `aldebaran` 用作日常集成分支及验收后自动合并的约定。用户委托管理提交，不等于授权自动合并或发布。

## 分支职责

| 分支 | 职责 |
| --- | --- |
| `master` | 同步 Excalidraw 开源上游，不接收产品定制功能 |
| `aldebaran` | 产品主分支，仅接收用户批准发布的版本 |
| `develop` | 主开发分支，集成经过验收且用户确认可合并的任务 |
| `feat/*`、`fix/*`、`chore/*` | 次开发分支，从最新本地 `develop` 创建，分别用于功能、修复和维护 |

- 所有代码和规范修改均在次开发分支进行，包括小修复。`master`、`aldebaran`、`develop` 不直接编写修改。
- 一个任务分支对应一个完整任务；相关前后端可以一起修改，不混入无关任务。按可独立运行的边界提交。
- 开始前核对分支、工作区、未提交用户文件和基准提交。不使用整仓库暂存，不默认提交笔记、计划或 `prompt.md`。
- 若首次落地时不存在 `develop`，从当前 `aldebaran` 创建，不移动已有分支或迁移数据。

## 开发、验收与两级批准

1. 从 `develop` 建立任务分支，记录基准，开发并完成相关测试。在固定 3009 验收。
2. 提交可审查的代码，说明功能变化、测试证据和已知限制，等待用户确认该任务可以合并。自动测试通过或 AI 自行判断验收完成不能替代用户确认。
3. 获得任务合并批准后，将任务分支合入 `develop`。用户暂不合并时保留分支与提交，不删除、不发布。
4. 只有用户另行明确批准发布具体候选提交，才能将 `develop` 中批准的版本合入 `aldebaran`。不夹带批准后新增的提交。
5. 更新正式服务需要明确的发布授权；仅批准 Git 合并不代表要求部署。用户明确要求“发布到正式版”时，可一并完成发布合并与部署。

“功能没问题／可以合并”只批准当前任务进入 `develop`，不批准进入 `aldebaran` 或更新 3010。一次消息明确同时批准两级操作时无需重复询问。

- 默认快进合并。目标已前进时，先在任务分支合入最新目标，解决冲突并重跑受影响检查；审查后代码发生实质变化时重新提交用户确认。
- 集成分支无法快进发布时，先在任务分支解决分歧并验收，不直接在产品主分支处理冲突。
- 合并前重新核对用户审查的提交和当前目标；批准针对具体代码，不能覆盖之后的实质变化。
- 不自动 rebase、reset 已有分支、强制推送或改写提交历史。默认不推送远端。
- 任务合入 `develop` 后可删除本地任务分支；未合并分支不自动清理。删除前核实提交已被保留，不因远端跟踪配置误删未集成工作。
- 发布前说明建议的 `vX.Y.Z` 版本号及提交，用户批准后创建标签；不移动已有标签。回退用历史构建或新增回退提交，不重置历史和用户数据。

## 同步开源上游

- 核实远端仓库身份；当前 `origin` 是用户仓库，不能假定它就是 Excalidraw 官方上游。不因例行开发自动拉取或同步上游。
- 用户要求同步时，先检查 `master` 与已核实上游的差异。既有 `master` 可能包含历史定制提交，不直接重置为官方历史；无法快进时报告差异并另行确定保留方式。
- 将上游更新接入产品时，从 `develop` 创建 `chore/upstream-YYYYMMDD`，在该分支合入更新后的 `master`，处理兼容问题并测试。
- 用户确认后合入 `develop`，另行批准发布后才进入 `aldebaran`。不能从 `master` 直接更新正式产品。

## 环境与交付

- 开发和验收只用 3009，固定数据目录 `.local-data/preview/notes/`；更新程序不更换数据集。测试样例唯一命名，只清理本次创建的记录。
- 正式版 3010 使用原 `notes/`。发布前等待在途任务结束并备份正式数据；未经授权不更新该服务。3001 属于其他项目，禁止停止或替换。
- 合并代码不迁移、覆盖或复制笔记、聊天和应用数据；开发与正式数据保持独立。
- 交付记录任务分支、基准和功能提交、测试结果及未验证项、批准范围、是否合并及发布。待批准时明确停留在哪一级，不能用“已完成”暗示已上线。

本 skill 是开发流程规范，不是已实现的 harness、Git 权限墙或自动合并工具。产品交互与视觉要求另读 [产品工程 skill](../excalidraw-product-engineering/SKILL.md)。
